## 模块一：用户研究报告

> 方法论来源：`ux-strategize` 技能框架（NNGroup Empathy Map + Ulwick ODI JTBD + Switch/Moesta Forces）

### 1.1 用户画像（Proto-Persona）

基于作品集 Demo 的实际使用场景（面试官浏览评估 + 潜在用户产品体验），提炼两类核心用户画像：

#### 画像 A：面试官（主要用户）

| 维度 | 描述 |
|------|------|
| **角色** | 互联网公司招聘经理/产品负责人 |
| **Tech-Comfort** | 7-8/10（熟悉各类产品原型工具） |
| **核心 JTBD** | 在 3-5 分钟内判断候选人是否具备产品经理核心能力 |
| **关键焦虑** | 作品集信息密度低→浪费时间；Demo 体验差→质疑执行力；风格不专业→质疑审美 |
| **行为模式** | 首屏 10 秒决定是否继续 → 快速扫描能力标签 → 点击 1-2 个 Demo 深入体验 → 形成初步判断 |
| **信息偏好** | 数据驱动（量化成果）、案例完整度（背景→方案→结果）、交互流畅度 |

#### 画像 B：产品体验者（次要用户）

| 维度 | 描述 |
|------|------|
| **角色** | 对 AI 产品感兴趣的用户/同行 PM |
| **Tech-Comfort** | 5-6/10（有基础产品使用经验） |
| **核心 JTBD** | 快速理解产品价值，体验核心功能 |
| **关键焦虑** | 功能复杂不知从何开始；隐私安全不确定；使用成本不透明 |
| **行为模式** | 着陆页→核心功能→决定是否深入 |

### 1.2 共情地图（Empathy Map — NNGroup 四象限）

基于 `ux-strategize` 的 NNGroup 4-quadrant 框架：

#### 面试官共情地图

```
┌─────────────────────────────────────────────┐
│  看到 SEES                                    │
│  · 大量候选人的作品集，风格各异                    │
│  · 项目描述堆砌功能点，缺乏量化成果                 │
│  · Demo 加载缓慢或交互生硬                        │
│  · "会做原型"和"懂产品"的差距明显                   │
├──────────────────────┬──────────────────────┤
│  做 DOES              │  听 HEARS             │
│  · 30秒内扫描首屏      │  · "候选人做过AI产品"    │
│  · 快速跳转到Demo体验   │  · "作品集链接在简历里"   │
│  · 对比多个候选人作品集  │  · HR推荐说"产品sense好" │
│  · 记录关键亮点和疑虑   │  · 行业对AI PM要求提高    │
├──────────────────────┴──────────────────────┤
│  想 THINKS / 感 FEELS                         │
│  · 想："这个人能不能上手干活？"                     │
│  · 想："项目是真实做的还是包装的？"                  │
│  · 感：时间紧迫，希望快速找到信号                    │
│  · 感：看到结构清晰的作品集会放松                    │
│  · 感：Demo卡顿时会质疑候选人执行力                  │
└─────────────────────────────────────────────┘
```

### 1.3 客户力量分析（Forces Diagram — Switch/Moesta）

```
  推动力量 PUSH                    阻碍力量 HABIT
  ─────────────                    ─────────────
  · AI PM岗位需求增长               · 面试流程固定(简历→面试)
  · 需要快速筛选候选人               · 习惯看PDF作品集
  · 希望看到真实产品能力             · 对在线Demo信任度低

  吸引力量 PULL                    焦虑力量 ANXIETY
  ─────────────                    ─────────────
  · 交互Demo比PDF更有说服力         · 担心Demo数据造假
  · 完整方法论展示产品思维           · 加载慢影响体验
  · 多项目覆盖体现能力广度           · 信息层级混乱浪费时间
```

**策略**：降低 ANXIETY（确保加载速度<2s、信息层级清晰、数据可信）→ 放大 PULL（交互体验+方法论+量化成果）

──────────┼──────────────┼───────────────┼───────────────┼──────────────

### 1.5 用户研究报告核心发现

| 发现编号 | 来源 | 核心洞察 | 影响优先级 |
|---------|------|---------|-----------|
| UR-01 | Journey Map | 首屏 10 秒决定去留，能力矩阵必须一眼可读 | P0 |
| UR-02 | Forces/Anxiety | Demo 加载慢（>2s）直接导致候选人被淘汰印象 | P0 |
| UR-03 | Empathy Map/Thinks | 面试官最关心"项目是不是真实做的"→Demo 必须可交互 | P0 |
| UR-04 | JTBD | 面试官要在 3-5 分钟内看完核心信息→信息层级必须清晰 | P0 |
| UR-05 | Persona/Tech-Comfort | 面试官 Tech-Comfort 7-8→不需要手把手引导，但需要清晰导航 | P1 |
| UR-06 | Forces/Habit | 面试官习惯 PDF→在线作品集需要提供"快速浏览模式"等效体验 | P1 |
| UR-07 | Empathy Map/Feels | 信息层级混乱引发焦虑→导航体系+进度条缓解 | P1 |

## 模块三：交互原型设计

> 方法论来源：`ux-wireframe` Artifact→Design 翻译矩阵 + 屏幕映射模式 + 交互状态全覆盖

### 3.1 Artifact → Design 翻译矩阵

基于 `ux-wireframe` 的翻译框架，将 UX 研究产物转化为具体交互设计决策：

| UX 产物 | 驱动的交互设计 | 不只是标签文本 |
|---------|--------------|--------------|
| 共情地图/Thinks | 信息层级：能力矩阵置顶，一眼可读 | 不只是"技能列表" |
| JTBD/核心任务 | CTA 按钮大小和位置：Fitts 定律→大按钮靠近拇指区 | 不只是"查看详情" |
| Forces/Anxiety | 信任信号：隐私承诺卡片、数据真实性、加载速度 | 不只是"隐私声明" |
| Journey Map | 页面序列和情感节奏：首屏冲击→深度案例→广度补充 | 不只是"页面列表" |
| VPC/Pain-Gain | 先缓解痛点再展示收益：先展示能力矩阵再展开详情 | 不只是"功能介绍" |
| Persona/Tech-Comfort | 复杂度校准：面试官7-8级→信息密度适中，不需要手把手 | 不只是"简洁设计" |

### 3.2 交互状态全覆盖（所有 Demo 通用）

基于 `ux-wireframe` 要求——"All states: loading, success, error, empty — never just happy path"：

| 状态 | 触发条件 | 设计方案 |
|------|---------|---------|
| **空状态 Empty** | 列表/看板/搜索无数据 | 插画（CSS 绘制）+ 引导文案 + CTA 按钮 |
| **加载状态 Loading** | 异步操作中 | <500ms: shimmer 骨架屏；>500ms: 进度条 + 品牌色脉冲 |
| **成功状态 Success** | 操作完成 | 绿色 toast + 对勾图标；重要操作: confetti 微庆祝 |
| **错误状态 Error** | 操作失败/表单验证 | 红色边框 + 错误文案（实时反馈）；网络错误: 重试按钮 |
| **焦点状态 Focus** | 键盘 Tab 导航 | `focus-visible` 蓝色外轮廓 2px |
| **禁用状态 Disabled** | 条件不满足 | 灰色 + opacity 0.5 + cursor not-allowed |
| **Hover 状态** | 鼠标悬停 | 轻微上移 + 阴影加深 + cursor pointer |
| **Active 状态** | 点击中 | 缩放 0.97 + 颜色加深 |

### 3.3 核心 Demo 交互原型规格

#### 3.3.1 pet-vaccine.html — 宠伴（P0）

**屏幕序列**（基于 Journey Map 阶段映射）：

| 屏幕 | 名称 | 核心交互 | 状态覆盖 |

## 模块五：可用性测试方案

> 方法论来源：`ux-evaluate` 六维评估模型 + `williamzujkowski/standards` 启发式评估标准

### 5.1 评估模型（六维评分体系）

基于 `ux-evaluate` 的加权评估框架：

| 维度 | 权重 | 评估标准 | 工具/方法 |
|------|------|---------|----------|
| **启发式评估** (Heuristic) | 20% | Nielsen 10 项可用性启发式 | 专家走查 |
| **策略对齐** (Strategy Alignment) | 25% | Demo 交互是否对齐用户研究发现 | 交叉校验 |
| **可访问性** (Accessibility) | 20% | WCAG 2.1 AA 合规 | 自动化+人工检查 |
| **认知负荷** (Cognitive Load) | 15% | Miller 7±2 / Hick 定律 / 渐进披露 | 认知走查 |
| **流程连贯** (Flow Coherence) | 10% | 跨页面导航、旅程阶段覆盖、死胡同检测 | 流程测试 |
| **认知走查** (Cognitive Walkthrough) | 10% | 4 问可发现性 + 成功率 | 任务测试 |

### 5.2 Nielsen 10 项启发式检查清单

| # | 启发式 | 检查方法 | 期望结果 |
|---|--------|---------|---------|
| 1 | **系统状态可见性** | 每个操作后检查是否有反馈 | 加载/成功/错误状态全覆盖 |
| 2 | **系统与真实世界** | 术语是否使用用户语言 | 无技术术语，中英文间有空格 |
| 3 | **用户控制与自由** | 误操作后能否撤销/返回 | Esc 关闭弹窗，返回不刷新状态 |
| 4 | **一致性与标准** | 同类操作是否一致 | 所有按钮/卡片/输入框样式统一 |
| 5 | **错误预防** | 高风险操作前是否有确认 | 删除/提交前弹窗确认 |
| 6 | **识别而非回忆** | 操作选项是否可见 | 不需要记忆操作路径 |
| 7 | **灵活性与效率** | 是否有快捷操作 | 键盘快捷键/批量操作 |
| 8 | **美学与极简** | 信息是否刚好够用 | 无冗余装饰/无用信息 |
| 9 | **帮助用户识别错误** | 错误信息是否有指导性 | "密码需含大写字母"而非"密码无效" |
| 10 | **帮助与文档** | 复杂功能是否有说明 | 可折叠介绍区/流程导览 |

### 5.3 认知负荷测试方案

| 定律 | 测试方法 | 通过标准 |
|------|---------|---------|
| **Miller 7±2** | 统计每屏同时展示的信息块数 | ≤ 7 个独立信息块 |
| **Hick 定律** | 统计每步操作的可选项数 | 每步 ≤ 5 个选项 |
| **Fitts 定律** | 测量主要 CTA 按钮尺寸和距离 | 主按钮 ≥ 44px，靠近拇指区 |
| **渐进披露** | 检查复杂功能是否分步展示 | 不在首屏展示所有细节 |
| **Von Restorff** | 检查关键信息是否有视觉突出 | 核心数据用大字/颜色突出 |

### 5.4 测试执行方案

#### 5.4.1 专家走查（Heuristic Walkthrough）

| 项目 | 内容 |
|------|------|
| **测试人数** | 2-3 名产品/设计背景评估者 |
| **测试范围** | 全部 P0 Demo + index.html |
| **测试任务** | 按 Journey Map 完成全流程（接触→探索→评估→决策） |
| **评分方式** | 六维评分，每维度 1-5 分，加权计算总分 |
| **输出物** | 评估报告（问题清单 + 严重度 0-4 + 改进建议） |

#### 5.4.2 认知走查（Cognitive Walkthrough）

针对每个核心任务，回答 4 个问题：

1. **可发现性**：用户是否知道该执行这个操作？（看到按钮/入口）

**宠伴案例应用**：
```
宠伴·健康台账 | 本地OCR + PWA | Tesseract.js + localStorage

问题：
- 80%宠物主用纸质记录疫苗，数据丢失率60%
- 现有宠物App需注册+云端存储，隐私顾虑阻碍数字化
- OCR识别需上传云端，敏感信息泄露风险

方案：
- 判断：OCR识别可用本地模型实现，精度满足需求
- 协作：AI自动识别 + 人工确认修正
- 权衡：本地OCR精度略低（85% vs 云端95%），但零隐私风险

技术选型：
- Tesseract.js：浏览器端OCR，无需服务器
- localStorage：本地存储，用户完全控制数据
- PWA：离线可用，无需安装

结果：
- 零隐私风险：用户数据永不离开设备
- OCR准确率85%：满足疫苗证明识别需求
- 用户留存提升40%：隐私信任带来粘性
```
